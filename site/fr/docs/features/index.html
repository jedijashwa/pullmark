Fonctionnalités

La visite, groupée par activité : lire, réviser, parcourir GitHub, éditer, et faire ressortir les documents. PullMark n'est délibérément pas un client de révision complet — il montre le Markdown d'un changement ; vos outils habituels restent les bons pour le code.

Lecture

  • Un rendu fidèle à GitHub — tableaux, listes de tâches, notes de bas de page, alertes, <details> repliables, coloration syntaxique, diagrammes Mermaid et maths KaTeX ($…$ / $$…$$), le tout hors ligne. Un paragraphe réduit à [toc] devient une table des matières cliquable ; ==highlight==, ~sub~, ^sup^ se rendent aussi.
  • Cliquez pour inspecter — images, diagrammes et formules en bloc s'ouvrent dans une vue avec panoramique et zoom ; Save As… et Share exportent exactement ce que vous inspectez (les diagrammes en vrais SVG).
  • Des fichiers vivants — les documents se réaffichent dès l'enregistrement depuis n'importe quel éditeur ; les images et liens relatifs se résolvent, et cliquer un lien vers un autre fichier Markdown l'ouvre sur place (en aperçu quand il vit dans un emplacement ouvert).
  • Navigation — le plan en barre latérale (⌥⌘O), la recherche dans la page ⌘F, la recherche ⇧⌘F dans tous les fichiers de la barre latérale, et ⌘K Open Quickly (ouvrir rapidement) pour les titres, fichiers, PR et récents — ou collez-y directement un chemin ou une URL GitHub.
  • Le blame à hauteur de lecture — une discrète gouttière d'auteurs : un avatar par suite de blocs, survolez pour le commit, cliquez pour l'historique des lignes. L'API de blame de GitHub quand le fichier vit sur GitHub, un simple git blame sinon.
  • Confort de lecture — thèmes, largeur du contenu, numéros de ligne (Réglages), zoom façon navigateur, clair/sombre, plein écran, et la position de lecture mémorisée par document.

Réviser des pull requests

  • Diffs rendus — blocs ajoutés, supprimés et modifiés surlignés dans la page rendue, diffs mot à mot là où la retouche est assez petite pour rester lisible, en inline ou côte à côte (⌥⌘L), plus le Source Diff brut (⌘2) et le Result final (⌘3). Les paragraphes déplacés reçoivent une discrète pastille « moved » au lieu du bruit rouge-plus-vert.
  • Les fils de révision sur place — les commentaires existants apparaissent sous les blocs qu'ils discutent ; survolez un bloc pour Comment Now (commenter maintenant), Add to Review (ajouter à la révision) ou Insert Suggestion (insérer une suggestion) — et le crayon édite le bloc en suggestion. Les révisions s'envoient avec un verdict, ou s'enregistrent sur GitHub comme révision en attente.
  • Où en est la PR — l'en-tête de la vue d'ensemble montre la décision de révision (approuvée, modifications demandées, révision requise), le verdict de chaque réviseur en avatars badgés avec les réviseurs attendus à côté, et une capsule de checks CI qui s'ouvre sur la liste complète — durées, étiquettes « required », et un lien vers les journaux de chaque check. Le tout se rafraîchit discrètement chaque minute.
  • La conversation, lisible — une seule chronologie sur la vue d'ensemble : commentaires et verdicts dans l'ordre, les commentaires en ligne de chaque révision imbriqués sous son résumé, avec le fichier discuté nommé sur la carte. Réactions, édition et suppression de vos propres commentaires, et le champ de commentaire au pied de la chronologie. Activé pour tout le monde (Settings ▸ General ▸ Reviewing permet de ranger les fils).
  • Reste à jour — les PR ouvertes sont vérifiées chaque minute ; une bannière propose de rafraîchir quand la branche avance, et vos brouillons survivent. Les commentaires écrits hors ligne se mettent en file et s'envoient dès que possible.
  • Demandes de révision — les PR qui attendent votre révision, dans la barre latérale avec compteurs non lus. Les images de PR et les liens relatifs au dépôt se résolvent au commit de la PR.

GitHub, sans le navigateur

  • Les liens Markdown s'ouvrent dans l'app — cliquez un lien github.com/…/blob/… et PullMark le rend (le premier clic pose la question ; ⌘-clic inverse votre choix par défaut). Une barre de provenance épingle owner/repo @ ref · path avec un chemin de retour vers GitHub.
  • Parcourez des dépôts entiers — chargez l'arborescence Markdown d'un dépôt dans Emplacements, changez de branche, comparez avec d'autres branches, consultez le blame — les dépôts privés utilisent les identifiants que les PR utilisent déjà, et rien de ce qui est récupéré ne touche jamais le disque.
  • Branches et worktrees — les copies locales portent une pastille de branche ; son menu ouvre les worktrees comme emplacements à part et lit les autres branches à distance. Le local l'emporte toujours sur le distant quand un worktree a déjà la branche.

Éditer et committer

  • Éditer sur place — le crayon d'un bloc (ou ⌘E pour tout le document) transforme les blocs en éditeurs à l'intérieur de la page rendue ; ⌘↩ enregistre, Échap annule. Les enregistrements sont protégés contre un fichier qui change en dessous, et versionnés pour Revert Last Edit (annuler la dernière édition).
  • Committer depuis l'app — ⌃⌘K ouvre la feuille de commit du dépôt du fichier : choisissez les fichiers, écrivez le message, poussez si vous voulez, avec un garde-fou avant de committer directement sur main.

Comparer avec l'historique

  • N'importe quel fichier, n'importe quelle révision — le bouton Compare de la barre d'outils (l'horloge et le chevron) diffe le fichier de travail contre n'importe lequel de ses 25 derniers commits, ou n'importe quelle branche locale ou distante — rendu, avec les mots modifiés surlignés, exactement comme une pull request. Un petit point sur le bouton signale des changements non commités.
  • « Qu'est-ce que je viens de changer ? » — un élément de menu (View → Compare with Last Commit) ou une commande shell (pullmark --diff file.md, voir la CLI). Le diff suit le fichier qui continue de changer — regardez les modifications d'un agent atterrir, surlignées, au fil des enregistrements.

Faire sortir les documents

  • Export — PDF (une page continue) ou HTML entièrement autonome ; Share (partager) envoie le document partout où macOS sait le porter.
  • Copier, en deux saveurs — ⌘C donne du texte riche pour Docs/Slack ; ⌥⌘C donne le Markdown sous-jacent.
  • Imprimer — ⌘P, à 100 % quel que soit le zoom.
  • Quick Look (Coup d'œil) — Espace dans le Finder prévisualise le Markdown avec le rendu de PullMark lui-même.

Une barre d'outils à vous

Clic droit sur la barre d'outils — ou View → Customize Toolbar… — pour la palette de personnalisation native : sortez ce que vous n'utilisez jamais, réorganisez le reste, ajoutez un Flexible Space. Chaque type de vue garde sa propre disposition, mémorisée d'un lancement à l'autre : un fichier local, une doc GitHub, un fichier de pull request et la vue d'ensemble de PR sont des barres d'outils distinctes, et vous personnalisez chacune pendant que vous y êtes — comme la fenêtre de rédaction de Mail garde sa propre barre.

Au-delà de la panoplie par défaut, la palette contient des éléments qui démarrent masqués : une bascule Source brute, Zoom In / Actual Size / Zoom Out, le sélecteur Content Width (largeur du contenu), Add Margin Note (ajouter une note de marge, tant que la fonctionnalité est activée), et pour les docs GitHub Share — la page github.com du document, jamais un lien brut — et Reload, qui re-résout une branche vers sa pointe actuelle et reste désactivé, avec la raison, pour les documents ouverts à un commit précis. Prêt à l'emploi, rien ne change ; la palette garde le reste. La barre d'outils liste les éléments de chaque vue.

Tout le reste

  • Fenêtres et onglets — ⌘N ouvre une fenêtre indépendante ; fusionnez en onglets natifs. Les ouvertures externes atterrissent dans la fenêtre au premier plan.
  • La commande pullmark — fichiers, dossiers et worktrees depuis n'importe quel terminal. Voir Ligne de commande.
  • Le contrôle de l'app par défaut — faites de PullMark le gestionnaire des .md en un clic, et il remarque si une mise à jour fait sauter l'association.
  • Mises à jour intégrées — des versions signées et notarisées, avec mise à jour en un clic et une feuille What's New (quoi de neuf).
  • Posture de confidentialité — le contenu GitHub est récupéré via l'API et gardé en mémoire, et les documents ne sont jamais copiés nulle part. La page confidentialité raconte tout.
